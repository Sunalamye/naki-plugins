## 決策

1. **v0.1 只做對局內自家外觀（F1–F3）**。（第二版由決策 11 取代：F1 移到 v0.1b。）理由：等長改寫 `authGame` 回應自家那筆就做得到，不送任何東西給伺服器，也不需要 Naki 端新工作。
2. **大廳類功能（F4–F9）全部排在 v1**，前置為 PV2-B2、PV2-C、`json` 型別。理由：都要在 repeated 欄位補元素，等長做不到。
3. **換裝請求用 `respondLocally`，不用 `rewriteSend`**。理由：大廳解鎖本來就卡變長改寫，與 `respondLocally` 同一個 probe；`rewriteSend` 只會多一個伺服器看得到的異常心跳，不會更早交付。放棄的折衷「等長換皮膚＋`rewriteSend` 中和」：只有半套功能、要開放所有插件的 L3、伺服器看得到異常。
4. **`NotifyAccountUpdate` 用變長改寫兩個子欄位，不 drop**。理由：同一則通知帶道具、任務等正當更新，drop 會讓客戶端狀態與伺服器分叉。
5. **登入回應只做等長就地改 `avatar_id`，不整包重編**。理由：`ResLogin` 含 `access_token`，Swift 也從它取 `account_id`。
6. **`owned` 未知時一律本地回應**；**L3 總開關關著時不做大廳解鎖**。理由：守住「伺服器不收到未擁有的宣稱」，寧可少一次真實換裝。（第二版由決策 9、10、12 細化：未知的類別不補入；撤銷與 L3 關閉由 N1 守。）
7. **id 不寫死**：v0.1 手動輸入，v0.2 設定頁從 `lqc.lqbin` 抓目錄，抓不到就退回手動輸入。
8. **授權**：CC0-1.0，與本 repo 既有插件一致。

9. **撤銷與送出 fail-closed 寫成 v1 硬性前置 N1、N2**（審查第 1、2 條）。理由：插件停用、自動停用、拋錯、L3 關閉時插件本身不在場或被拒，只有 Naki 能保證不送出。Naki 不接受時，插件停在 v0.2／v0.1b。
10. **send 側與 receive 側的失敗方向相反**：receive 不確定就原樣通過（I8），send 證明不了擁有就不送出（I9）。
11. **v0.1 縮小為裝扮與稱號**（審查第 3 條）。理由：對局內唯一帶自由內容的外送是 `broadcastInGame`，插件攔不住；角色與皮膚可能改變表情面板。F1 改為 v0.1b，前置是不點擊的 live 確認與 v0.2 目錄。
12. **擁有清單逐類分 `unknown`／`complete`，按登入世代失效；與其他改寫插件同 method 時停用該類**（審查第 4、5 條）。
13. **守衛方法擴大為 19 個；扣道具或發獎勵的操作回本地錯誤，不假裝成功**（審查第 3、7 條）。
14. **角色、皮膚、頭像整組提交，varint 長度依實際值判定**（審查第 8 條）。
15. **v0.1 加 Naki 端等價測試 N7 為發布前置**（審查第 9 條）。
16. **v1 保留舊 `views` 字串 key，由設定頁明確遷移**（審查第 10 條）。
17. **Naki 需求分成硬性前置、v0.1 前置、建議、撤回四組；撤回 `ctx.setSetting` 與 `authGame` 強制限制**（審查第 13 條）。
18. **F5、F7、F8 在 v1 預設關閉**，直到擁有來源或控制欄位 live 確認（審查第 4、11 條）。

## Deviations

- **D1：「地鐵模式」不設計，列為不做。** 派工清單有這一項，但 Naki 已查證的 MajsoulMax 功能描述（`plugin-system-design.md` §2）沒有它，而派工又禁止上網讀它的原始碼。不知道它是什麼就無法判斷是否只影響本機，保守地列為不做。要做的話，先由主線提供它公開 README 的功能描述。
- **D2：功能清單沒有重新到網上核對。** 派工允許參考 MajsoulMax 公開 README 的功能描述，但本工作包只用 Naki 已查證的轉述（`plugin-system-design.md` §2，2026-08-09），沒有連網。理由：不得上網抓原始碼，連到它的 repo 又容易越線。代價：README 若在 2026-08-09 之後新增功能，本設計沒有涵蓋。
- **D3：「自訂名稱」列為不做**，雖然它只影響本機。理由：Naki 的 Swift 端從 `authGame` 的 `nickname` 取名字，改它會連帶改 Naki 的狀態；而且截圖可能誤導他人。屬保守選擇。
- **D4（第二版已修正）：對 Naki 端多提了三項現行 v2 計畫沒有的需求**（第一版設計 §8.2 第 10、11、13 條）：遊戲頁插件寫回自己設定的通道、`authGame` 欄位限制是否強制、唯讀的 L3 開關狀態。第 11、13 條只是建議。另外回報一處文件漂移（第一版第 12 條）。
  第二版依審查第 13 條撤回 `ctx.setSetting` 與 `authGame` 強制限制，`ctx.outboundAllowed` 降為建議。
- **D5：v1 新增的 Naki 端需求 N1、N2 超出 `plugin-v2.md` 的原語設計**，而且 N2 改變了 `plugin-v2.md` §4.4 對守衛方法的 fail-open 語意。審查第 1、2 條要求把它們寫成前置，所以提出；是否接受由 Naki 端決定，不接受時採保守選項：v1 不做。
- **D6：v1 的錯誤碼未定。** 本地錯誤回應用哪個錯誤碼，遊戲才會正常顯示，目前沒有證據。保守選項：錯誤回應的方法在 live 確認前不開放，F4 隨之不開。
- **D7：熱重載期間不插入 message 事件是推論。** 依據是 `PluginRegistry.enableScript` 把停用、設 grant、重跑源碼放在同一段腳本。未在 App 內驗證；推論不成立時同樣由 N1 接手。
